# Threshold

Внешний клиент для Minecraft: отдельный процесс-оверлей, читающий состояние игры
из JVM снаружи. Без инжектов (никаких DLL в игру, Java-агентов или модов) и с
минимумом записи в память — чтение по умолчанию, любая запись проходит через
отдельный гейт с логированием и указанием причины.

## Принцип работы

```
┌──────────────────┐   ReadProcessMemory    ┌─────────────────────────┐
│  threshold.exe   │ ─────────────────────► │  Minecraft (javaw.exe)  │
│  (оверлей D3D11) │    только чтение*      │  HotSpot JVM, jvm.dll   │
└──────────────────┘                        └─────────────────────────┘
        │  DWM композитит прозрачное layered-окно поверх игры
        ▼
  ImGui-меню / ESP и прочие фичи
```

\* запись существует как API (`mem::Process::writeBuf`), но процесс открывается
только с правами на чтение; права на запись выдаются явно на уровне фичи, и
каждый вызов пишется в лог с причиной.

### Версионная независимость — через VMStructs

HotSpot компилирует в `jvm.dll` таблицу `VMStructs` — самоописание всех
внутренних структур JVM (смещения полей `Klass`, `oopDesc`, `InstanceKlass`,
адреса статиков `Universe::_collectedHeap` и т.д.). Таблица находится в памяти
процесса по якорным парам строк (`Klass`/`_layout_helper`), проверяется по
известным ключам — и мы получаем все офсеты для **любой сборки JVM**, без
сигнатур под конкретные версии JDK. Поверх этого строится обход Java-кучи и
поиск объектов Minecraft (вне зависимости от версии, снапшота, загрузчика или
лаунчера — всё это просто разные JVM-процессы).

## Сборка

Требуется MSVC (x64), CMake и Ninja. В `tools/` лежат локальные CMake/Ninja
(скачиваются отдельно), MSVC берётся из установленных Build Tools.

```
build.bat          # configure + build (RelWithDebInfo)
```

Бинарник: `build/threshold.exe`. Лог: `build/threshold.log`.

## Управление

| Клавиша | Действие |
|---------|----------|
| `INSERT` | показать/скрыть меню (клик-сквозь выключается при открытом меню) |
| `END` | выход |

Пока Minecraft не запущен — панель висит со статусом «searching...». Найдя окно
процесса с `jvm.dll`, оверлей прилипает к клиентской области игры и двигается/
ресайзится вместе с ней.

## Структура

```
src/
  core/       лог (spdlog), конфиг (JSON), утилиты
  memory/     Process (RPM-обёртка, гейт записи), паттерн-сканер
  jvm/        VMStructs-парсер, JvmRuntime/JvmEnv, HeapReader (обход кучи),
              определение версии JDK
  mc/         поиск окон/процессов Minecraft (jvm.dll как маркер)
  overlay/    окно + D3D11 + DirectComposition (premultiplied alpha) + ImGui
  ui/         ImGui-меню (статус, таргет, JVM, куча, фичи)
  app/        оркестрация: attach, трекинг окна, главный цикл
```

| D3D11 + DXGI (нативные) | рендер оверлея с per-pixel альфой (FLIP_DISCARD + layered) |

## Роадмап

1. ~~**Обход Java-кучи**~~ ✅ G1-регионы → oop-итерация → ~8M объектов,
   параллельный обход + фоновый поток (~6-16 c, раньше 80).
2. ~~**Модель Minecraft**~~ ✅ Поля из `_fieldinfo_stream`, граф
   class_310 → field_1724 → class_746 → super-chain → class_1297 →
   field_22467 (Vec3) → живые координаты игрока в меню.
3. ~~**Маппинги версий**~~ ✅ `mappings/<version>.json` (классы + field-ID
   правила), версия из заголовка окна, fallback default.json/builtin 1.21.1.
   Для новой версии MC достаточно скопировать JSON и поправить field IDs.
4. **Фичи.** ESP (проекция через view-matrix из кучи), список сущностей
   (ClientLevel entity sections), HUD — всё на чтении.
5. **Ресерч-тулинг.** Zydis-резолв ссылок из кода jvm.dll для статиков, которых
   нет в VMStructs.

## Ускорение скана — что было медленно и как починено

- Кэш классов был `std::map` с поиском на каждый объект → плоский двухуровневый
  кэш (локальный per-thread + глобальный с мьютексом только на промахах).
- Совпадение с таргетами считалось на каждый объект строковыми операциями →
  теперь `mc`/`targetIdx` вычисляются один раз на класс.
- Имя Symbol читалось двумя RPM → один RPM (length+body смежные).
- Обход регионов распараллелен (до 6 потоков, очереди через atomic-индекс).
- Обрыв цепочки размеров перескакивал старты объектов (синглтоны терялись в
  зависимости от состояния GC) → ресинк ищет вероятный заголовок
  (mark&7==1 + валидный klass в кэше) и возобновляет цепочку.
- Скан уехал в фоновый поток: оверлей не фризится, статус «scanning heap...»,
  Rescan/отмена по флагу.

Гочча, на которую потратили время: `klassInfo()` вставлял запись в локальный
кэш без targetIdx, а `resolve()` обновлял только глобальную таблицу — локальная
«тень» затирала правильный индекс у того потока, который сам резолвил класс.

## Что узнали про JDK 21 (проверено на живой JVM)

JDK 21 сильно вычистил VMStructs; всё недостающее выводится эмпирически:

- Из VMStructs пропали `Universe::_narrow_oop_base/_narrow_klass_base/_shift`
  и `MemRegion::_*`. Офсеты `VMStructEntry` при этом стабильны:
  `{typeName, fieldName, dataTypeString, isStatic, offset, datum}` — 48 байт.
- `HeapRegionManager::_regions` в JDK 21 — не GrowableArray, а `G1HeapRegionTable`
  (`_base @16` → `HeapRegion*[]`, `_length @24`); `HeapRegion::_bottom/_top` @0/16.
- `GrowableArray<T>::_data` описан на инстанциации (`GrowableArray<int>`),
  `_len` — на базовом классе (`GrowableArrayBase`).
- Имена констант: `_lh_array_tag_oop_value` → `_lh_array_tag_obj_value`;
  layout helper хранит header size (биты 16–23) и element type (8–15).
- Сжатые klass-указатели на Windows: CDS-регион маппится на фиксированный
  `0x8_00000000`, narrow id = смещение от этого адреса (shift = 0). Статиков
  base/shift в VMStructs нет — Threshold выводит их сам: сэмплирует narrow id из
  Eden/Survivor/Old-регионов по вероятным заголовкам объектов (mark == 0x...001),
  проверяет гипотезы базы валидацией декодированных Klass* (layout helper + имя
  через `Symbol`) и кросс-чеком с `vmClasses::_klasses[]` (адреса фундаментальных
  классов известны из VMStructs-статиков).
- Размер инстанса калибруется на живой куче: перебор кодировок layout helper,
  побеждает та, что даёт самые длинные цепочки валидных объектов.
- Куча на этой конфигурации маппится на `0x6_00000000..0x640000000` (1 ГБ),
  первый регион — CDS-архив (ZIP-данные), в сэмплинге идут только eden/surv/old.
- Narrow oop (heap): base=0, shift=3 (нулевая кодировка — куча на 24 ГБ),
  выводится по игроку: декодированный объект обязан иметь klass id известного
  инстанса class_746.
- **ConstantPool на JDK 21**: записи — u64 от `cp+80` (1-based): Utf8 хранит
  `Symbol*` напрямую; Fieldref/Methodref = (nat<<16)|class; NameAndType =
  (desc<<16)|name; UnresolvedClass = (name<<16)|64; Integer/Double — инлайн.
- **`InstanceKlass::_fieldinfo_stream`** (JDK 21 заменил `_fields`) — массив u1,
  поток UNSIGNED5-чисел: `j k Field[j+k] 0`, где `Field := name sig offset
  access fieldflags Optionals`; опционалы (initval/gsig/group) присутствуют по
  битам fieldflags. Офсеты полей — в байтах. Источник формата:
  `oops/fieldInfo.hpp`, `utilities/unsigned5.hpp` (OpenJDK 21).

## Ограничения базы

- 32-битные JVM (старые беты на Java 6/7 x86) пока не поддерживаются —
  читаются только x64-процессы (детектится и логируется).
- Полноэкранный exclusive-режим (редкий для Java-издания) может перекрыть
  оверлей; оконный и borderless — полностью поддерживаются.
- Скан кучи — слабо консистентный снимок: GC во время скана может слегка
  исказить счётчики. Пересканирование — кнопкой в меню.
