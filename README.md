# Threshold

**Внешний клиент для Minecraft** — отдельный процесс-оверлей, который читает
состояние игры прямо из JVM снаружи и рисует поверх окна игры.

- **Без инжектов.** Никаких DLL в игру, Java-агентов или модов. Threshold —
  самостоятельное приложение, подключающееся к процессу игры через
  `ReadProcessMemory`.
- **Чтение по умолчанию.** Процесс игры открывается только с правами на чтение.
  Запись существует как API (`mem::Process::writeBuf`), но требует явного
  включения на уровне конкретной фичи, и каждый вызов логируется с причиной.
- **Версионная независимость.** Ни сигнатур под версии игры, ни таблиц офсетов
  под конкретные JDK — всё внутреннее устройство JVM читается из
  самоописания самой JVM (см. [Как это работает](#как-это-работает)).

| | |
|---|---|
| Платформа | Windows 10/11, x64 |
| Язык | C++20 |
| Игра | Minecraft Java Edition (любая версия, снапшоты, бетки) |
| Загрузчики | vanilla, Fabric, Forge, NeoForge (intermediary-маппинги) |

## Возможности

### ESP
- Рамки на сущностях с проекцией, корректной при любом FOV игры.
- **FOV подхватывается сам** — из `options.txt` инстанса (путь через PEB
  процесса игры), перепроверяется каждые ~2 секунды. Никаких ручных настроек.
- **Классификация сущностей** по цепочке наследования: `Mob`, `Player`,
  `Item`, `Projectile`, `ArmorStand` и прочее — с фильтрами по типам.
- Сглаживание позиций: тики игры (20 tps) интерполируются, рамки не «дёргаются».
- Дистанция видимости настраивается.
- Известная проблема обхода кучи (пропуск синглтона `Minecraft` при десинке
  обхода) решается восстановлением инстанса по back-reference от
  `GameRenderer` — модель поднимается даже если скан промахнулся.

### Меню (Metro UI)
- Тайловое меню в стиле Windows 8: категории, цвета, иконки (Segoe MDL2).
- Правая панель — настройки выбранного модуля: переключатели, слайдеры,
  фильтры типов сущностей, бинд клавиш.
- Статус-страница: PID и путь процесса, версия JDK, статистика скана кучи,
  найденные таргет-классы с количеством инстансов, координаты игрока.
- Кнопки Rescan / Dump / Dump Fields для диагностики прямо из меню.

## Как это работает

```
┌──────────────────┐   ReadProcessMemory    ┌─────────────────────────┐
│  threshold.exe   │ ─────────────────────► │  Minecraft (javaw.exe)  │
│  (оверлей D3D11) │    только чтение*      │  HotSpot JVM, jvm.dll   │
└──────────────────┘                        └─────────────────────────┘
        │  DWM композитит прозрачное layered-окно поверх игры
        ▼
  ImGui-меню / ESP и прочие фичи
```

\* запись — только через гейт с логированием, см. шапку.

Конвейер от запуска до работающего ESP:

1. **Поиск игры.** Перебор видимых окон; процесс-кандидат должен содержать
   `jvm.dll`. Версия игры парсится из заголовка окна.
2. **Разбор JVM.** HotSpot компилирует в `jvm.dll` таблицу `VMStructs` —
   самоописание всех внутренних структур (смещения полей `Klass`, `oopDesc`,
   `InstanceKlass`, адреса статиков и т.д.). Таблица находится по якорным
   парам строк и проверяется по известным ключам. Результат: все офсеты для
   **любой сборки JVM** — vanilla, Fabric, Forge и разные лаунчеры просто
   дают разные JVM-процессы.
3. **Обход кучи.** Через `VMStructs` строится список G1-регионов
   (`HeapRegionManager`), регионы обходятся параллельно (до 6 потоков),
   ~8.5 млн объектов за ~15 секунд. Для каждого объекта резолвится класс
   (имя через `Symbol`), цельные классы из маппингов собирают адреса
   инстансов. Скан идёт в фоновом потоке — оверлей не фризится.
4. **Модель игры.** Поля классов читаются из `InstanceKlass::_fieldinfo_stream`
   (JDK 21 формат, UNSIGNED5-поток) + разрешение имён через ConstantPool.
   Граф объектов: `Minecraft → player (class_746) → Entity (super-chain) →
   Vec3/повороты`, отдельно `ClientLevel → entityStorage → Int2ObjectMap`
   (карта сущностей), `GameRenderer → camera` (позиция и базис камеры).
5. **Рендер.** Отдельное layered-окно с per-pixel прозрачностью
   (D3D11 + DirectComposition, premultiplied alpha), прилипает к клиентской
   области игры, двигается и ресайзится вместе с ней.

### Определение сжатых указателей — эмпирически

JDK 21 вычистил из VMStructs статики `Universe::_narrow_klass_*` и
`MemRegion::_*`. Threshold выводит недостающее сам:

- **Narrow klass**: сэмплирование вероятных заголовков объектов из кучи →
  проверка гипотез базы декодированием `Klass*` (layout helper + имя) →
  кросс-чек с `vmClasses::_klasses[]`. На Windows CDS-регион маппится на
  фиксированный `0x8_00000000`, гипотеза подтверждается за один проход.
- **Narrow oop**: перебор гипотез (`{0, shift=3}`, `{heapBase, 0/3}`) с
  валидацией по классу декодированного объекта.
- **Размер инстанса**: калибровка на живой куче — побеждает кодировка
  layout helper с самыми длинными цепочками валидных объектов.

### Восстановление потерянных синглтонов

Последовательный обход кучи может десинхронизироваться и пропускать
1–2 объекта — от этого не застрахован ни один внешний обход. Синглтон
`Minecraft` восстанавливается по back-reference: `GameRenderer` (который
находится надёжно) держит единственное поле типа `Lnet/minecraft/class_310;`.
Поле ищется по дескриптору, а не по ID — работает на любых версиях.

## Маппинги версий

`mappings/<версия>.json` — таблица классов и правил полей для intermediary-имён:

```json
{
  "version": "1.21.1",
  "loader": "intermediary",
  "classes": {
    "minecraft": "net/minecraft/class_310",
    "localPlayer": "net/minecraft/class_746",
    "clientLevel": "net/minecraft/class_638"
  },
  "fields": {
    "player": { "owner": "minecraft", "name": "field_1724", "type": "Lnet/minecraft/class_746;" }
  }
}
```

- Версия определяется из заголовка окна игры; при отсутствии файла
  используется `default.json`, затем builtin-таблица 1.21.1.
- **Новая версия игры = скопировать JSON и поправить field-ID.** Классы и
  граф объектов не меняются.
- Поля, чей дескриптор однозначен, ищутся по типу — их ID менять не нужно.

## Сборка

Требуется Windows, MSVC (x64) — подойдут Visual Studio 2022 Build Tools —
CMake ≥ 3.20 и Ninja. В `tools/` лежат локальные CMake/Ninja (скачиваются
отдельно); если их нет, `build.bat` использует системные из `PATH`.

```
build.bat              # configure + build (RelWithDebInfo)
```

Бинарник: `build/threshold.exe`. Лог: `build/threshold.log` (+ ротация).

Зависимости (Dear ImGui docking, spdlog, nlohmann/json, Zydis) тянутся через
FetchContent в `external/` при первой конфигурации — интернет нужен один раз.

## Запуск и управление

1. Запустите Minecraft (любой лаунчер), зайдите в мир.
2. Запустите `threshold.exe`. Пока игры нет — панель висит со статусом
   «searching...». Найдя процесс с `jvm.dll`, оверлей прилипает к игре и
   запускает скан кучи (15–20 секунд на фоне, статус в меню).
3. INSERT открывает меню — включайте модули в правой панели.

| Клавиша | Действие |
|---------|----------|
| `INSERT` | показать/скрыть меню (клик-сквозь выключается при открытом меню) |
| `END` | выход |

```
src/
  core/       лог (spdlog, ротация), конфиг (JSON), утилиты
  memory/     Process — RPM-обёртка с гейтом записи; паттерн-сканер

              KlassReader — поля классов (_fieldinfo_stream + ConstantPool)
  mc/         поиск окон/процессов (jvm.dll как маркер); GameModel —

  overlay/    layered-окно, D3D11 + DirectComposition, ImGui-рендер
  ui/         Metro-меню (тайлы, категории, панель настроек)

mappings/     JSON-таблицы классов/полей по версиям игры
```

## Заметки о JDK 21 (проверено на живой JVM)

Справочное — то, что пришлось выяснить при работе без таблиц офсетов:

- `VMStructEntry` стабилен: `{typeName, fieldName, dataTypeString, isStatic,
  offset, datum}`, 48 байт; `isStatic` стоит **перед** offset/datum.
- `HeapRegionManager::_regions` в JDK 21 — не `GrowableArray`, а
  `G1HeapRegionTable` (`_base @16` → `HeapRegion*[]`, `_length @24`);
  `HeapRegion::_bottom/_top` @ 0/16. `GrowableArray<T>::_data` описан на
  инстанциации (`GrowableArray<int>`), `_len` — на `GrowableArrayBase`.
- Имена констант: `_lh_array_tag_oop_value` → `_lh_array_tag_obj_value`;
  layout helper хранит header size в битах 16–23, element type в 8–15.
- Сжатые klass-указатели: CDS-регион на Windows маппится на `0x8_00000000`,
  narrow id = смещение от него (shift 0). `Universe::_narrow_oop_*` /
  `_narrow_klass_*` из VMStructs удалены — только эмпирический вывод.
- Narrow oop: кодировка zero-based (`base=0, shift=3`) при куче на 24 ГБ —
  выводится по игроку: декодированный объект обязан иметь klass id
  известного инстанса `class_746`.
- **ConstantPool**: записи — u64 от `cp+80` (1-based). Utf8 хранит `Symbol*`
  напрямую; Fieldref/Methodref = `(nat<<16)|class`; NameAndType =
  `(desc<<16)|name`; UnresolvedClass = `(name<<16)|64`; Integer/Double —
  инлайн.
- **`InstanceKlass::_fieldinfo_stream`** (заменил `_fields`): массив u1,
  поток UNSIGNED5 (`j k Field[j+k] 0`, `Field := name sig offset access
  fieldflags Optionals`); опционалы — по битам fieldflags; офсеты полей в
  байтах. Источник формата: `oops/fieldInfo.hpp`, `utilities/unsigned5.hpp`
  (OpenJDK 21).
- Куча маппится на `0x6_00000000..0x640000000` (1 ГБ); первый регион —
  CDS-архив (ZIP-данные), в сэмплинге участвуют только eden/survivor/old.

## Ограничения

- Только 64-битные JVM. 32-битные процессы (старые бетки на Java 6/7 x86)
  детектируются и логируются, но не читаются.
- Exclusive fullscreen (редкость для Java-издания) может перекрыть оверлей;
  оконный и borderless режимы поддержаны полностью.
- Скан кучи — слабо консистентный снимок: GC во время скана может слегка
  исказить счётчики (позиции сущностей это не затрагивает).
- Forge/NeoForge с SRG/MCP-маппингами — в планах (формат таблиц уже готов).
